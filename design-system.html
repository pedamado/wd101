Chapter 01 • Literature Synthesis & Industry Standards

Why We Design Systems, Not Pages

A front-end style guide is more than a sticker sheet of buttons. Synthesizing the WD101 bibliography reveals how compositional hierarchy (Frost), shared pattern language (Kholmatova), single-source-of-truth tokens (Suarez & Anne), and content budgets (Kissane) converge in modern systems like IBM Carbon.

Compositional Hierarchy • 2016

Brad Frost — Atomic Design

Frost dismantles the print-era myth of static "pages" by organizing interfaces as nested matter: Design Tokens (Subatomic) → Atoms → Molecules → Organisms → Templates → Pages. Crucially, Chapter 3 insists that style-guide documentation chrome remain barebones and neutral so it never competes visually with live specimens, while Chapter 4 introduces the Interface Inventory audit to expose duplicated styles before writing CSS.

Shared Language & Dual Patterns • 2017

Alla Kholmatova — Design Systems

Kholmatova critiques purely mechanical size buckets when teams lack a shared domain vocabulary. She divides every design system into two interlocking layers: Perceptual Patterns (aesthetic voice, granite-and-neon contrast, typographic tension, spring motion physics) and Functional Patterns (concrete domain modules solving user tasks, such as a Schedule Row or Pass Simulator), governed along a strict-vs-loose spectrum.

Tokens & Living Specs • 2019

Suarez, Jina Anne et al. — Design Systems Handbook

Suarez, Sylor-Miller, Mounter, Stanfield, and Jina Anne (coiner of Design Tokens during the Salesforce Lightning system) formalize how design scales across design tools and codebases: pairing reusable UI components with explicit standards explaining Why, When, and When Not to use each pattern. Design tokens store subatomic visual decisions as platform-agnostic key-value pairs shared between Figma Variables and CSS Custom Properties.

Content-First & Industrial Rigor

Erin Kissane & IBM Carbon Design System

Following Kissane’s Content Inventory discipline, components never hold `Lorem ipsum`; real copy character limits, microcopy tone, and media aspect ratios dictate intrinsic box sizing. We pair this with IBM Carbon’s Neo-Grotesque Swiss grid discipline: the 2x Grid, an 8px spatial mini-unit (with 4px half-steps), contextual surface layering (canvas → surface → elevated), and Carbon’s 4-part component specification contract (Usage, Anatomy, States, Code/A11y).

Editorial Voice, Tone & UI Diction • 2010 / 2018

Chris Barr (Yahoo!) & Scott Kubie — Writing for Designers

Chris Barr & Yahoo! ground web writing in eye-tracking behavior (3-second gaze scans, front-loaded headings, self-descriptive links, inclusive global English, and exact UI verb pairs like Delete vs. Remove). Scott Kubie organizes all project text into Interface, Product, and Marketing Copy, replacing Lorem ipsum with a 4-phase workflow (Prepare → Compose → Edit → Finish), the Accuracy → Clarity → Brevity (ACB) editing ladder, context-adaptive Tone (Urgency, Scale, Emotion), and a shared Controlled Vocabulary.

Web Typography Triad • 2014

Jason Santa Maria — On Web Typography

Santa Maria separates mere legibility (decoding glyphs) from true readability (sustained comfort across saccadic eye jumps and word-shape fixations). He pairs versatile Workhorse body faces (tall x-height, open apertures) with expressive short-burst Moment/Display faces, locking in the interlocked Typographic Triad: user-honoring rem Font Size (≥ 16px), a 45–75ch Measure (80ch ceiling), and unitless 1.5–1.65 Leading.

Chapter 02 • Architectural Core

The Dual Cascade: Hierarchical Inheritance in CSS, Design Systems & Figma

Students often learn the “C” in Cascading Style Sheets as a browser conflict-resolution algorithm without realizing that Atomic Design Systems and Figma Variables/Variants run on the exact same principle: define high-level intent once at the root, inherit downwards automatically, and override only at the narrowest scope required.

1. The CSS Engine Cascade & DOM Inheritance

When a browser resolves every property on an element, it filters declarations through a strict priority waterfall before falling back to DOM tree inheritance:

  1. Origin & Cascade Layers (@layer): Unlayered rules beat layered rules; in DRUMTIKS '26, @layer reset, tokens, layout, components, interactive, xray; guarantees a component class always beats a reset rule—even at (0,0,0) specificity.
  2. Selector Specificity: :where() flattens resets and fallback groups to (0,0,0); base classes sit cleanly at (0,1,0); relational state selectors like .ticket-tier-card:has(input:checked) rise intentionally to (0,2,0).
  3. Scoping Proximity (@scope): @scope (.specimen-canvas) scopes festival components to their stage container so closer ancestors win without class-name collisions.
  4. DOM Property Inheritance: Typography (font-family, line-height), color (propagated into SVG icons via currentColor), and all --* custom properties flow down the DOM tree automatically.

2. The Design System Token & Atomic Cascade

In a design system, changing a single upstream decision propagates through four hierarchical tiers without touching component markup:

  1. Tier 1 — Primitive / Option Tokens: Context-free raw values (--prim-red-60: #e60000, --space-md: 1rem). Never referenced directly inside organisms.
  2. Tier 2 — Semantic / Decision Tokens: Role-based aliases carrying dark/light intent (--color-accent-red, --color-bg-surface: light-dark(#fff, #121316)).
  3. Tier 3 — Component-Scoped Tokens: Local hooks (--card-border, --btn-bg) overridden on state changes (:hover, :has(:checked)).
  4. Compositional Inheritance (Frost): Updating an Atom (e.g., .pill-badge radius or focus ring) automatically updates every Molecule (.program-item-card) and Organism (.hero-stage-card) containing it—just like editing a Main Component in Figma updates every nested Instance.
⚠️ Critical CSS Inheritance Gotcha with light-dark(): Because light-dark() resolves at computed-value time on inherited properties like color and accent-color, descendants only inherit the already-picked color—not the live light-dark() expression. Never register design-token custom properties with @property syntax: "<color>", and whenever a sub-surface overrides color-scheme (like our dark <pre> blocks or specimen preview toggles), always set an explicit background and re-declare color: var(--color-text-primary) and accent-color on that container!

1. Why :user-invalid Beats :invalid

  • Legacy input:invalid fires the instant a page loads or on the very first keystroke ("w"), shouting red errors prematurely.
  • :user-invalid defers error styling until the user commits a value (blur or submit), then clears the instant the format becomes valid!

2. Anatomy & Hint Placement

  1. Explicit <label for>: Persistent above field; never replace labels with vanishing low-contrast placeholders.
  2. Hint above input: Linked via aria-describedby so browser autofill popovers and virtual keyboards never cover format rules.
  3. Dual-cue feedback: Border + subtle surface shift + text/icon message below.

3. All 5 Field States

  • Pristine: Neutral 2px border; zero error noise.
  • Focused: 3px offset focus ring.
  • :user-invalid: Red border + rose tint + visible sibling .dt-error-msg + synced aria-invalid="true".
  • :user-valid: Emerald confirmation border + check caption.
  • disabled / [inert]: 45% opacity, removed from tab order.

4. Autofill & Progressive Fallback

  • Pair type="email" + inputmode="email" + autocomplete="email" so mobile keyboards, validation, and password managers reinforce one another.
  • Includes .user-invalid-fallback via a lightweight WeakMap blur listener + automatic aria-invalid synchronization.
